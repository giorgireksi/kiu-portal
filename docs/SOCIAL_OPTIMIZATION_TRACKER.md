## Current Findings

1. `social.html` is still a large standalone frontend with two major client-side surfaces: desktop social shell and mobile shell.
2. `social-mobile.js` no longer polls for navigation readiness; it now listens for the social runtime update event and load completion.
3. The remaining major risk is the desktop `social-page.js` bundle, which is still too large to treat as a single unit even after the community, lost-found, alerts, messages, and profile panel extractions.
4. The route root no longer rebuilds through one `host.innerHTML = ...` swap. `renderSocialPageNow()` now keeps a stable shell and updates flash, topbar, command, center, rail, drawer, mobile nav, toasts, and overlay regions separately.
5. `social.html` no longer starts with a separate loading placeholder card; it now ships the same stable root shell structure that the runtime keeps after boot, with one non-blocking in-shell loading message in the center region until live data arrives.
6. The route now has an explicit panel ownership map below, the duplicated top-level panel entry names are isolated into explicit legacy helpers so one canonical renderer owns each live panel dispatch, the route shell no longer loads `assets/js/features/ui.js`, and the community, lost-found, alerts, messages, and profile panels now lazy-load from dedicated companion modules.
7. The page-local rerender work is now closed: boot no longer waits for directory bootstrap before the first live render, the standalone page no longer re-injects a duplicate social runtime on itself, account enrichment now finishes after the first hydrated paint, transparency refreshes can stay scoped to the touched social shell regions, and the community panel now mounts its real layout shell immediately while the deferred desktop module finishes loading.
8. The latest seeded desktop artifact still shows shared-shell long-task pressure, but that remaining budget miss now sits with the cross-route shared runtime work tracked under the master audit rather than with a page-local social rerender loop.
9. The social route remains one of the most important visual surfaces in the repo, so every performance change must preserve the current design language.
10. The live social panel strings are now source-clean again for separators, visibility labels, and high-signal placeholders in the desktop route runtime.
